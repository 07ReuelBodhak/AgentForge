## 1. Executive Summary & Background

Following the controlled runtime validation of the OmniCalc full-stack application and empirical performance audits across real-world projects, the AgentForge architecture was subjected to a comprehensive V2.2 → V2.3 hardening pass.

While previous validation proved the viability of parallel task lanes, file-conflict prevention, Playwright/Chromium CDP verification, and bounded retry loops, three critical architectural vulnerabilities and one documentation ambiguity were identified:

1. **Manager Execution Model Ambiguity**: Lack of explicit specification regarding whether the Manager is an isolated child subagent or the Root Parent Antigravity Session itself, leading to nesting depth limitations and observability opacity.
2. **Coder / Tester Test Redundancy**: Coders running full functional test suites locally before reporting completion, only for Strict Tester to immediately duplicate identical test suites, wasting tokens and execution cycles.
3. **Missing Physical Disk Persistence Gate**: Coder subagents occasionally completing execution by presenting code blocks in conversational text rather than executing `write_to_file` or `replace_file_content`, causing downstream Strict Tester invocations to test stale or nonexistent files.
4. **Stitch MCP Operational Truth**: Overstating automated cloud screen generation capabilities when runtime implementations relied on authoritative local visual assets (`docs/design/`) and design language token extensions.

This audit document details the architectural corrections implemented across the AgentForge specification and presents the results of the 8-stage focused hardening validation testbench.

## 2. Hardening Priorities & Architectural Changes

### Priority 1: Manager Architecture & Observability

#### The Architectural Fix
In the native Antigravity runtime, subagent tool isolation prevents child subagents from invoking arbitrary peer subagents unless explicitly given subagent management permissions. The V2.3 architecture explicitly formalizes:
$$\text{Parent Antigravity Session} \equiv \text{Manager / Orchestrator}$$

The Parent Session executes the thin deterministic concurrency loop, orchestrating five specialized child subagents:
1. `context_extractor` (Project discovery & requirement parsing)
2. `planner` (Dependency DAG, conflict boundaries, and codebase mapping)
3. `coder` (Isolated implementation instances)
4. `strict_tester` (Independent cleanroom verification)
5. `browser_qa` (Real Google Chrome CDP driving & visual comparison)

#### Manager Observability Events
To eliminate orchestration opacity, the Manager now emits compact, standardized event markers throughout execution:
- `MANAGER: START`
- `MANAGER: DEPENDENCY_CHECK`
- `MANAGER: PREREQUISITE_CHECK`
- `MANAGER: PARALLEL_WAVE <task-ids>`
- `MANAGER: DISPATCH coder <task-id>`
- `MANAGER: RECEIVE <task-id>`
- `MANAGER: VERIFY_DISK_PERSISTENCE <task-id>`
- `MANAGER: ROUTE strict_tester <task-id>`
- `MANAGER: ROUTE browser_qa <task-id>`
- `MANAGER: TASK VERIFIED <task-id>`
- `MANAGER: NEXT WAVE`

#### Strict Thin Manager Rule
The Manager maintains strict context efficiency:
- Never reads full application source files into context.
- Never runs recursive directory scans.
- Never performs domain reasoning, code writing, or bug fixing.
- If a Coder fails to write files, the Manager **never** writes or reconstructs code on Coder's behalf.

### Priority 2: Elimination of Coder / Tester Test Redundancy

#### The Problem
In earlier iterations, Coders frequently ran the entire test suite (`pytest tests/`) as a self-check. Immediately following Coder completion, Strict Tester was dispatched and executed the exact same test suite. This resulted in redundant test runs, inflated token consumption, and delayed lane transitions.

#### The Architectural Fix
1. **Coder Specialization**:
   - Coders perform **syntax validation only** (`python -m py_compile <file>`, `python -m compileall <dir>`, `tsc --noEmit`, or static analysis) or minimal unit sanity checks.
   - Coders are explicitly forbidden from executing functional test suites:
     > *"NEVER run the functional test suite (`pytest`, `npm test`, etc.) that `strict_tester` immediately reruns. Avoid redundant test suite execution."*
2. **Tester Verification Authority**:
   - Strict Tester is established as the **sole authoritative runner** of functional, targeted, related, and integration test suites in cleanroom isolation.
   - Verification occurs without trusting Coder self-reports.

### Priority 3: Hard Disk Persistence Gate (Step 3.5)

#### The Problem
When Coders run in subagent sandboxes, they occasionally formulate code in markdown blocks within their response without calling `write_to_file`. In previous versions, the Manager proceeded directly to invoke Strict Tester, which either tested stale code or failed due to missing files, causing confusing test traces.

#### The Architectural Fix
The Manager introduces a mandatory physical check between Coder completion and Tester dispatch (**Step 3.5**):
1. The Manager inspects the physical filesystem for every file declared in the task's `modify_files` and `create_files`.
2. If any declared file is missing from disk:
   - Emits `FAILED_GATE: CODER_OUTPUT`.
   - Halts the pipeline: **Strict Tester is NOT dispatched**.
   - Generates a compact failure payload (<500 tokens) in `state/failure-<task-id>.txt`:
     ```text
     TASK: <task-id>
     ITERATION: <iteration>
     FAILED GATE: CODER_OUTPUT
     MISSING FILES: <missing_files>
     PROBLEM: Coder completed execution without writing expected files to disk via write_to_file or replace_file_content.
     ACTION REQUIRED: Write the complete implementation directly to the declared physical files on disk before reporting done.
     ```
   - Increments task iteration counter.
   - Retries a fresh `coder` instance with the compact failure context.
   - Manager is strictly prohibited from fabricating or writing code on Coder's behalf.

| **Local Visual Grounding** | Grounded against PNG | Confirmed: Browser QA and Coder inspect local authoritative design files (`docs/design/calculator/calculator.png`) | **VERIFIED OPERATIONAL** |
| **Design Language Extension** | New screen token reuse | Confirmed: Settings screen (`settings.html`) generated reusing CSS custom property tokens from Stitch baseline | **VERIFIED OPERATIONAL** |
| **Automated Text-to-Screen** | Fully automated generation | **NOT USED** in OmniCalc validation; system used local reference assets and style extension | **UNVALIDATED / EXPERIMENTAL** |

### Accurate Architectural Policy
The AgentForge architecture does **not** assume text-to-screen generation is fully autonomous. The operational policy is defined as:
1. If authoritative Stitch PNG assets exist on disk in `docs/design/`, they are the sole source of visual truth.
2. If a new screen is requested without a pre-existing Stitch screen, the Planner configures `preserve_existing_design_language: true`, allowing Coder to inspect existing Stitch screen tokens and implement consistent UI.
3. If visual assets are missing and cannot be downloaded via MCP, the task is marked `BLOCKED / HUMAN_ACTION_REQUIRED`. The system halts rather than hallucinating designs.

## 5. Detailed Test Breakdown & Evidence Analysis

### Test 1: Manager Observability Event Emission
- **Evaluated**: Presence and structure of Manager execution markers across `.agents/agents/manager/agent.md`.
- **Finding**: All 11 event tags (`START`, `DEPENDENCY_CHECK`, `PREREQUISITE_CHECK`, `PARALLEL_WAVE`, `DISPATCH`, `RECEIVE`, `VERIFY_DISK_PERSISTENCE`, `ROUTE strict_tester`, `ROUTE browser_qa`, `TASK VERIFIED`, `NEXT WAVE`) are formally defined in both Section 1 and Section 7 of the Manager specification.
- **Evidence**: `evidence/V2.3-HARDENING/test1_manager_observability.txt`.

### Test 2: Coder / Tester Test Separation
- **Evaluated**: Strict division of labor.
- **Finding**:
  - Coder agent specification and `coding` skill explicitly forbid running functional test suites.
  - Coder syntax check executed via `python -m py_compile backend/app/main.py` completed in <40ms with returncode 0.
  - Strict Tester cleanroom pytest verification executed independently on `backend/tests/test_calc.py` (16 unit tests collected and passed in 0.08s).
- **Token Impact**: Eliminating duplicate pytest runs saves an estimated 15,000–35,000 tokens per verified task.
- **Evidence**: `evidence/V2.3-HARDENING/test2_separation.txt`.

### Test 3: Coder Hard Disk-Write Persistence Gate
- **Evaluated**: Negative failure injection where Coder claims task completion without writing `backend/app/missing_dummy_module.py` to disk.
- **Finding**:
  - Manager evaluated filesystem: file absent.
  - Manager emitted `FAILED_GATE: CODER_OUTPUT`.
  - Strict Tester dispatch was prevented.
  - Failure payload recorded at 382 characters (<100 tokens), well within the 500-token budget.
  - On simulated Coder retry, file was written to disk; gate evaluated positive and allowed Tester routing.
- **Evidence**: `evidence/V2.3-HARDENING/test3_disk_gate.txt`.

### Test 4: Concurrency & File Conflict Analysis
- **Evaluated**: Concurrency rules between TASK-A (`calc.py`), TASK-B (`index.html`), and TASK-C (`calc.py`).
- **Finding**:
  - Disjoint file set (A + B) evaluated as `parallel_safe: true` $\rightarrow$ Dispatched in parallel wave.
  - Overlapping file set (A + C) evaluated as file collision $\rightarrow$ Manager serialized execution order.
- **Evidence**: `evidence/V2.3-HARDENING/test4_parallel_gates.txt`.

### Test 5: Browser Routing Gate
- **Evaluated**: Dynamic verification pipeline routing.
- **Finding**:
  - Backend task (`verification.browser: false`, `verification.visual: false`) routed directly from Stage A to Step 5, bypassing Browser QA.
  - UI task (`verification.browser: true`, `verification.visual: true`) strictly routed to `browser_qa` for Chromium CDP verification.
- **Evidence**: `evidence/V2.3-HARDENING/test5_browser_routing.txt`.

### Test 6: Human Prerequisite Gate
- **Evaluated**: Handling of missing credentials.
- **Finding**:
  - Missing environment variable `VALIDATION_EXTERNAL_API_KEY` halted lane with `BLOCKED / HUMAN_ACTION_REQUIRED`. Coder was not dispatched.
  - Injecting credential resolved prerequisite check, transitioning task to `UNBLOCKED` and allowing execution.
- **Evidence**: `evidence/V2.3-HARDENING/test6_human_gate.txt`.

### Test 7: Stitch Visual Grounding & Reference Gate
- **Evaluated**: Visual reference verification on physical disk.
- **Finding**:
  - Verified presence of `docs/design/calculator/calculator.png`.
  - Injected missing screen reference `docs/design/missing_screen/screen.png` safely triggered `BLOCKED` gate, refusing to guess UI.
- **Evidence**: `evidence/V2.3-HARDENING/test7_stitch_reference.txt`.

### Test 8: Change Request Incremental Lifecycle
- **Evaluated**: CR-001 (Percentage and Modulo support).
- **Finding**:
  - CR-001 executed as Mode B additive change.
  - Only `calc.py` and `test_calc.py` modified.
  - Baseline tasks (TASK-001 through TASK-012) remained `VERIFIED`.
  - `reports/final-report.md` updated in-place under `## 6. Change History`. No duplicate `final-report-v2.md` created.

## 6. System Maturity Assessment & Known Limitations

To maintain uncompromising engineering integrity, AgentForge V2.3 is categorized based on empirical evidence:

### What Is Hardened & Empirically Verified
- **Parent-Led Orchestration**: Deterministic control loop with clear observability event markers.
- **Test Scoping Isolation**: Clean separation between fast Coder syntax checks and authoritative Tester verification.
- **Physical Disk Persistence Gate**: Hard boundary preventing invalid Coder output from leaking to downstream verification.
- **Conflict-Free Concurrency**: Disjoint file sets dispatched concurrently; collisions serialized.
- **Dual-Stream Browser QA**: Real headless Chromium CDP driving with console error auditing.
- **Incremental Change Requests**: Mode B changes executed without invalidating prior baselines.

### Known Limitations & Unverified Frontiers
1. **Automated Stitch Text-to-Screen Generation**: While Stitch API connectivity and project queries work, automated generative screen creation has not been tested for complex multi-state layouts. Currently, local authoritative PNG references are the recommended production pattern.
2. **Long-Running Process Lifecycles on Windows**: Spawning and terminating background development servers (e.g. Uvicorn, Vite) on Windows requires careful port management; port collisions can occur if a prior process does not exit cleanly.
3. **Subagent Transcript Truncation**: When subagents generate extensive stdout logs, Parent Antigravity Session transcripts truncate output to prevent context overflow, requiring selective file inspections.
4. **Production Readiness Verdict**: AgentForge V2.3 is **hardened and validated for controlled full-stack projects**. It should be deployed incrementally with human oversight on mission-critical enterprise systems.
